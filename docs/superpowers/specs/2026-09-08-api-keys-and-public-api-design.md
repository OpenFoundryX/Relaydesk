# API keys & the public API — design

**Date:** 2026-09-08
**Status:** approved in chat, pending written review
**Slice:** 6 (follows slice 5, password reset)

Builds on `2026-09-04-tenancy-and-inbox-core-design.md` (slice 1), which
remains binding for multi-tenancy, sessions, the conversation and message
model, and the error envelope. Where this document is silent, slice 1 governs.

## 1. What this builds

A workspace can mint an API key and use it to drive its own inbox from
outside the console: create conversations from its own systems, read and
update them, reply, and manage labels.

This is the first slice in a group of four that together make Relaydesk a
platform rather than an application:

1. **API keys and the public API** — this document.
2. A domain event stream (internal, ships nothing user-visible alone).
3. Signed webhooks, delivered from (2), managed and consumed through (1).
4. AI triage, triggered by (2), acting as a principal defined here.

It is first because the other three depend on it. A webhook receiver needs
somewhere to call back into. An AI action needs a principal to be attributed
to that is neither a human nor "Relaydesk". And an idempotent create endpoint
(§6) is what makes a retried webhook delivery safe, so it has to exist before
retries do.

## 2. What already exists, and what it obliges

Three console pages were built as UI shells against `apps/web/lib/mock/settings.ts`
and have no backend: `settings/api-keys`, `settings/custom-webhooks`, and
`settings/ai-triage`. This slice makes the first of them real. The other two
are left as shells; slices 3 and 4 claim them.

The shells are not neutral. `apps/web/components/settings/code-sample.tsx`
publishes a worked request in four languages:

```
POST https://api.relaydesk.dev/v1/conversations
Authorization: Bearer rd_live_your_key_here
{ customer_email, customer_name, subject, message, priority, external_id, metadata }
```

That sample is the contract this slice has to keep. It settles the mount path
(§5), the auth header, the snake_case body, and it names two fields the
`Conversation` model does not have — `external_id` and `metadata` (§6).

`apps/web/components/settings/api-key-dialog.tsx` settles two more things: the
secret is shown exactly once, at creation, and a key is rotated by creating a
new one and deleting the old one. There is no reveal-again and no in-place
rotate.

## 3. Decisions

**D1 — A key is a machine principal, not an impersonation of its creator.**
A key belongs to the workspace. It carries its own name, its own scopes, and
its own identity in the audit trail. It does not inherit a membership.

The alternative — a key that resolves to the `User` who created it — needs no
changes to `WorkspaceScope` at all, and was rejected for two reasons. The
audit trail would lie: "Sara closed this ticket" when Sara has been on leave
for a month and a Zapier automation closed it. And the key's fate would be
tied to an employment record: when Sara is removed from the workspace, either
her key keeps working (a departed employee's credential still writing to
production) or it stops (a production integration broken by an HR action). A
workspace-owned credential has neither problem.

**D2 — `WorkspaceScope` is not modified.** The obvious expression of D1 is to
make `WorkspaceScope.user` nullable and let both principal kinds flow through
one dependency. That is rejected: `scope.user` is non-null at every one of its
call sites today, several of which pass it straight into a service, and
loosening the type turns a compile-time guarantee into a runtime audit of
every console route for a feature no console route uses.

Instead the surfaces stay separate. `workspace_scope` remains session-only and
unchanged. v1 routes depend on a new `api_scope`, which resolves a key. The
two meet only at the service layer, through D3.

**D3 — Services take an `Actor`, not a `User`.** A small value object in
`relaydesk/services/actors.py`:

```python
@dataclass(frozen=True, slots=True)
class Actor:
    name: str
    user_id: uuid.UUID | None
    api_key_id: uuid.UUID | None
```

with `Actor.for_user(user)` and `Actor.for_key(key)` constructors. The ~10
service functions in `services/conversations.py` that currently take
`actor: User` take `Actor` instead.

This is a smaller change than it looks, because the persistence layer was
already built for it. `conversations.record()` already accepts
`actor: User | None` with an `actor_name` fallback "for activity generated by
inbound mail rather than a signed-in user", and writes to
`activity_events.actor_user_id` (nullable) and `activity_events.actor_name`.
`Message` has the same nullable-FK-plus-name-snapshot shape. `Actor` is the
name for a pattern the code already follows twice.

**D4 — A key's actions are attributable to the key, not just to its name.**
Two new nullable columns: `activity_events.actor_api_key_id` and
`messages.author_api_key_id`, both `ON DELETE SET NULL`.

The name snapshot in `actor_name` is enough to *display* history. The foreign
key is what answers "show me everything this key did" — which is the question
asked on the day a key is suspected of having leaked, and which cannot be
retrofitted onto history written before the column existed. Two nullable
columns is a cheap insurance premium against the one scenario where the
answer matters most.

**D5 — Permissions are a closed set of `resource:action` scopes.**

| Scope | Grants |
|---|---|
| `conversations:read` | List and read conversations and their messages |
| `conversations:write` | Create a conversation; change status, priority, assignee |
| `messages:write` | Send a reply to the customer |
| `contacts:read` | List and read contacts |
| `labels:read` | List labels |
| `labels:write` | Create a label; add and remove labels on a conversation |

Six scopes, fixed. A write scope does **not** imply its read scope; the
console dialog offers presets so this is not a burden in practice.

`messages:write` is deliberately not folded into `conversations:write`.
Changing a status is an internal bookkeeping action; sending a reply puts mail
in a customer's inbox under the workspace's name. A triage bot that labels and
prioritises should not be one bug away from mailing customers, and the only
way to express that is to make it a separate grant.

Reusing the `admin`/`agent` role enum was rejected: a key pasted into a
third-party tool should carry the least privilege that tool needs, and the
role enum has no vocabulary below "everything an agent can do".

**D6 — v1 gets its own router and its own schemas.** Not shared with the
console routes.

The existing schemas are console-shaped in ways that would be actively
embarrassing as a public contract. `ConversationOut` carries `age: "3h"` and
`date: "Sep 4"` — strings rendered for one particular sidebar, in the
workspace's timezone, computed at serialisation time. It carries `has_draft`,
which is about an agent's unsent text. `CamelModel` makes every field
camelCase. A public API that served these would freeze a UI's rendering
decisions into a compatibility surface, and the next inbox refactor would be
a breaking API change.

So: `relaydesk/api/v1/` and `relaydesk/schemas/v1.py`, snake_case, ISO-8601
timestamps, no derived display fields. Both surfaces call the same services;
only the edges differ.

**D7 — v1 mounts at `/v1`, beside `/api`, not under it.** `/api` is the
console's private surface and stays that way. `/v1` is the public contract.

This makes the published sample true with no proxy rewriting: hosted at
`api.relaydesk.dev/v1/conversations`, self-hosted at
`localhost:8000/v1/conversations`. It also makes the boundary legible in the
route table — a reader can see which routes are a promise to third parties
and which are free to change.

**D8 — v1 is deliberately narrow.** Conversations, messages, labels, contacts.
Twelve endpoints (§5).

No knowledge base, team, channel or workspace endpoints. Every endpoint in v1
is a promise, and the cost of a promise is paid at every future refactor.
Team and channel writes in particular are a serious privilege surface for a
leaked key, and nothing has asked for them. Additive expansion later is
compatible; retraction is not.

**D9 — One key prefix, `rd_`.** The mock shows `rd_live_` and `rd_test_`.
Rejected. Both places that carry the string are corrected to match:
`apps/web/lib/mock/settings.ts` and the published sample in
`apps/web/components/settings/code-sample.tsx`.

There is no sandbox workspace. A key labelled `test` would read and write the
same production data as one labelled `live`, at which point the label is not a
safety property but an invitation to assume one. Somebody pastes the test key
into a test suite and mails real customers. When a sandbox workspace exists —
it is listed as a gap in the feature research — the split can be introduced
then, meaning what it says.

**D10 — Per-key rate limiting gets a new counter, not `services/ratelimit`.**

The existing limiter is correct for what it was built for and wrong here. It
takes a `pg_advisory_xact_lock` per call and inserts one row per request,
which is the right trade at five portal submissions per hour. At a couple of
requests per second per key it means every same-key request serialises on one
lock — turning a bulk import into a queue — and writes a row per call into a
table pruned only by a sweep.

The new counter is a fixed window: one row per `(api_key_id, minute)`, written
with `INSERT … ON CONFLICT DO UPDATE SET count = count + 1 RETURNING count`.
One round trip, no lock, no serialisation between concurrent callers, and at
most one row per key per minute. The cap is `api_key_rate_limit_per_minute` in
`config.Settings`, defaulting to 120. Swept on the existing beat schedule,
alongside `sweep_rate_limits`.

A fixed window admits the usual burst at a window boundary (up to 2× the limit
across two adjacent windows). That is accepted: this limit exists to bound a
runaway integration and protect the database, not to defeat an adversary — an
API key holder is an authenticated tenant acting on their own data, which is a
materially different threat model from the anonymous portal form.

## 4. Authentication

`Authorization: Bearer rd_<secret>`, the same header shape as a session token.
The secret is `secrets.token_urlsafe(32)` from `security/tokens.generate_token`;
only `hash_token`'s SHA-256 digest is stored, in a unique-indexed column.

SHA-256 rather than argon2, for the same reason `Session` uses it: the token is
256 bits of CSPRNG output with no low-entropy structure, so there is no
dictionary to slow down, and a password KDF on the hot path of every API
request would only buy latency. Resolution is a single unique-index lookup on
the digest, so there is no per-candidate comparison and no timing channel of
the kind `authenticate()` guards against.

A key is rejected — `401`, uniform message — if the hash does not resolve, if
`revoked_at` is set, or if `expires_at` has passed.

The stored `prefix` is `rd_` plus the first four characters of the secret, kept
only so the settings list can show which key a row is (`rd_7f2a···`). Four
characters of a 43-character token narrow nothing: an attacker who could
brute-force the remaining 39 could brute-force all 43.

`last_used_at` is updated at most once an hour, reusing the interval
`resolve_session` already uses for `Session.last_seen_at`. Writing it on every
request would put a write on every read path for a field whose only consumer
is a "Last used" label in a settings list.

**The model.** `api_keys`: `workspace_id` (FK, cascade), `name`, `prefix`
(display only), `token_hash` (unique), `scopes` (a Postgres text array of D5
enum values, validated at the schema edge),
`created_by_user_id` (nullable, `SET NULL` — the key outlives its creator,
per D1), `last_used_at`, `expires_at` (nullable; no expiry by default),
`revoked_at` (nullable).

Deletion in the console is a revoke (`revoked_at`), not a row delete, so that
`activity_events.actor_api_key_id` keeps resolving to a name.

## 5. API surface

### Public, key-authenticated — `/v1`

| Method | Path | Scope |
|---|---|---|
| GET | `/v1/conversations` | `conversations:read` |
| POST | `/v1/conversations` | `conversations:write` |
| GET | `/v1/conversations/{id}` | `conversations:read` |
| PATCH | `/v1/conversations/{id}` | `conversations:write` |
| GET | `/v1/conversations/{id}/messages` | `conversations:read` |
| POST | `/v1/conversations/{id}/messages` | `messages:write` |
| PUT | `/v1/conversations/{id}/labels/{label_id}` | `labels:write` |
| DELETE | `/v1/conversations/{id}/labels/{label_id}` | `labels:write` |
| GET | `/v1/labels` | `labels:read` |
| POST | `/v1/labels` | `labels:write` |
| GET | `/v1/contacts` | `contacts:read` |
| GET | `/v1/contacts/{id}` | `contacts:read` |

`GET /v1/conversations` filters on `status`, `priority`, `assignee_id`,
`label_id` and `updated_since`, and paginates by opaque cursor. `updated_since`
is what makes a polling sync possible before webhooks exist, and is why it is
in v1 rather than deferred.

`POST /v1/conversations` takes the body the code sample publishes, verbatim.
Conversations it creates carry `channel = api` — the enum member exists today
with nothing behind it. `customer_email` resolves through the existing
`services/contacts` upsert, so a repeat customer reaching the API lands on the
same `Contact` row as one reaching the inbox by mail; the API does not get a
second contact identity.

### Console, session-authenticated — `/api/api-keys`

`GET`, `POST`, `DELETE /{id}`. Admin only, via the existing
`WorkspaceScope.require_admin()`. `POST` returns the plaintext secret; it is
the only response that ever contains it.

### Errors

The slice-1 envelope, unchanged: `{"error": {"code", "message"}}`.

- `401` — key absent, unresolvable, revoked or expired.
- `403` — key lacks the scope, with a message naming it ("This key needs the
  `messages:write` scope."). Safe to disclose: the caller holds the key and can
  see its scopes in the console.
- `404` — a resource in another workspace, indistinguishable from one that does
  not exist. The slice-1 isolation contract, unchanged.
- `429` — over the per-key limit, with `Retry-After`. Every response carries
  `X-RateLimit-Limit` and `X-RateLimit-Remaining`.

## 6. Idempotency, and the two new conversation columns

**`Conversation.external_id`** — `String(200)`, nullable, with a **partial**
unique index on `(workspace_id, external_id)` where `external_id IS NOT NULL`.
Partial for the reason already documented on `uq_messages_channel_external`:
Postgres treats NULLs as distinct, so a plain unique index would permit
unlimited duplicate `(workspace_id, NULL)` rows while appearing to constrain.

`POST /v1/conversations` carrying an `external_id` that already exists in the
workspace returns the existing conversation with `200`, not a duplicate with
`201`. This is what makes an interrupted import safe to re-run, and it is why
this belongs here rather than in the webhooks slice: a delivery-retry design
without an idempotent create endpoint to retry *into* is not a design.

**`Conversation.meta`** — JSONB, mapped to a `metadata` column and exposed as
`metadata` on the wire. The Python attribute cannot be `metadata`; that name is
taken by SQLAlchemy's Declarative API. Capped at 8 KB serialised and 50 top-level
keys, validated at the schema edge, so it stays a place for `order_id` and
`plan` and does not become a blob store inside the conversations table.

## 7. Multi-tenancy

A key names exactly one workspace. `api_scope` resolves the key, loads its
workspace, and every v1 query filters on `workspace_id` from the key — never
from a path or body parameter. There is no cross-workspace key and no way to
ask for another workspace's data; a foreign UUID resolves to `404` by the same
mechanism a session's would.

This is the slice-1 contract applied to a new principal, not a new one.

## 8. Out of scope

Webhooks (slice 3). AI triage (slice 4). Per-key IP allowlists. Generated
client SDKs. An MCP server. Knowledge base, team, channel and workspace
endpoints. Key expiry reminders and automatic rotation. A sandbox workspace,
and with it the `live`/`test` split (D9).

## 9. Testing

Per endpoint: an authorised call succeeds; a key from another workspace gets
`404`; a revoked key gets `401`; an expired key gets `401`; a key missing the
required scope gets `403`; an over-limit key gets `429`. Cross-workspace
isolation is asserted per endpoint rather than once, matching how the existing
suite treats it.

Beyond the matrix:

- A repeated `external_id` returns the first conversation and creates no second
  row; two concurrent creates with the same `external_id` resolve to one row
  rather than an unhandled `IntegrityError`.
- A `metadata` body over either cap is refused at the edge with `422`.
- An activity event written by a key has `actor_user_id IS NULL`,
  `actor_api_key_id` set, and the key's name in `actor_name`.
- The plaintext secret appears in exactly one response and is not recoverable
  from `GET /api/api-keys`.
- `last_used_at` is not written twice within the throttle interval.
- The counter admits exactly `limit` calls in a window and refuses the next,
  under concurrency.

## 10. Known risks carried

**A leaked key is full access to its scopes until noticed.** There is no IP
allowlist and no anomaly detection. The mitigations shipped are least-privilege
scopes (D5), per-key attribution so the damage is legible after the fact (D4),
and immediate revoke. A key with `messages:write` that leaks can mail a
workspace's customers, which is the worst case and is stated plainly here so
that the scope picker's presets are designed against it.

**The fixed window admits a 2× boundary burst.** Accepted in D10.

**`metadata` is unindexed.** It is retrievable per conversation, not queryable
across them. If filtering on `metadata` is ever wanted, that is a GIN index and
a query-language decision, deliberately not made here.

**v1 becomes a compatibility surface the day it ships.** D8's narrowness is the
mitigation; it is not a free one. Every subsequent inbox change has to ask
whether it changes a v1 response, and nothing in the codebase enforces that
question. A response-shape snapshot test on the v1 schemas is the cheapest
enforcement and is included in the implementation plan.
