# Email Channel — Design

**Sub-project 2 of the Relaydesk backend.** Builds on
`2026-09-04-tenancy-and-inbox-core-design.md` (slice 1), which is the binding
authority for everything it already settled: multi-tenancy, sessions, the
conversation and message model, and the API conventions. Where this document
and slice 1 disagree, section 3 below records the amendment explicitly.

## 1. Goal

Make the inbox real. Today conversations exist only because `make seed`
created them, and an agent's reply is written to the database and goes
nowhere. After this slice, mail sent to a workspace's address becomes a
ticket, an agent's reply is delivered to the customer, and a customer's reply
threads back onto the same conversation.

Three things blocked on having no mailer are also unblocked here: team
invites (disabled in slice 1 and documented as such in the README),
assignment notifications, and delivery feedback when an address is dead.

## 2. Scope

**In scope**

- A Celery/RabbitMQ worker tier and the scheduled jobs it runs.
- Inbound: IMAP polling of one deployment mailbox, MIME normalization,
  workspace routing, classification, thread resolution, contact upsert, and
  conversation create-or-append.
- Outbound: SMTP delivery of agent replies, with retry and delivery state.
- Attachments: stored, scoped, and served safely.
- Bounce handling.
- Invites re-enabled, gated on a token that only reaches the invited address.
- Assignment notification email with a per-user preference.
- `settings/channels` wired to real data.

**Not in scope**

- The customer portal (magic-link contact sessions, portal ticket list).
  Slice 1's spec placed this with the channels slice; it is a second
  authentication system next to user sessions, with its own tenant-isolation
  surface, and it becomes slice 3 with its own spec.
- Per-workspace IMAP/SMTP credentials. See decision D4.
- Provider webhooks (Postmark, Mailgun, SES), the Gmail API, Discord, the
  Tickets API, one-click import.
- Custom sending domains and DKIM signing per workspace.
- AI generation of any kind (slice 4).

## 3. Amendments to slice 1's spec

Slice 1 section 11 anticipated this slice. Two of its statements are wrong
and are corrected here.

**A1 — Message-ID origin.** Slice 1 says outbound "must store the Message-ID
returned by the SMTP server." SMTP returns a queue identifier, which is
local to that server and meaningless to any other host; the `Message-ID`
header is generated by the sender. Relaydesk mints the `Message-ID` before
handing the message to SMTP and stores that value. The intent of the
original line — that outbound messages must have a stored identifier for
customer replies to thread onto — is preserved exactly.

**A2 — Portal ticket list moves.** Slice 1 assigned it here. It moves to
slice 3, for the reason in section 2.

**A3 — `channel_accounts` holds no credentials.** Slice 1 named the table
without specifying its columns. Under decision D4 the deployment owns a
single mailbox configured through the environment, so no row in this
database ever contains a mailbox password.

## 4. Decisions

Recorded with their rationale so later slices can be checked against them
rather than relitigating them.

**D1 — Slice boundary: email channel only.** The customer portal is slice 3.

**D2 — Transport: SMTP send and IMAP poll.** No provider account, no DNS
setup, and it works from behind NAT, which a webhook cannot. `docker compose
up` must produce a working mail path with no external service, so GreenMail
ships in the development stack as both the SMTP sink and the IMAP source
(section 5).
Provider webhooks can be added later as another adapter behind the same
`InboundMessage` normalization without redesign.

**D3 — Worker: Celery with a RabbitMQ broker.** Chosen over a
Postgres-backed queue for its scheduling (Beat), mature tooling, and
familiar operational story. Two consequences are load-bearing and appear
throughout this document:

- Celery is synchronous and this codebase is async end to end. Tasks are
  thin synchronous wrappers that call `asyncio.run()` on an async
  implementation, which reuses the existing `services/` layer unchanged. A
  parallel synchronous data-access path is explicitly rejected: it would
  require reimplementing the `workspace_id` predicates that every service
  function carries, and duplicated tenant scoping is how slice 1's
  cross-tenant defects were written.
- Enqueue is not transactional. The API can commit a row and then fail to
  publish, so `messages.delivery_state` plus a reconciler task closes the
  window (section 9).

**D4 — Inbound model: forwarding to a deployment mailbox.** The deployment
owns one mailbox, credentialed through the environment. Each workspace gets
a generated ingest address; the customer forwards their own `support@` to
it; the poller routes by recipient. Relaydesk therefore stores no customer
mailbox credentials at all, and a database compromise grants no mailbox
access. The cost is the routing fragility handled in section 7.2.

**D5 — Ingest tokens are random, not derived.** A workspace's ingest address
is `<slug>-<token>@<inbound domain>` where the token is 6 bytes of
`secrets.token_hex`, unique, and unrelated to the slug or id. A derivable
address would let anyone who can guess a workspace's name inject tickets
into its queue.

**D6 — Attachments are stored on a mounted volume, content-addressed.**
Local filesystem, keyed by SHA-256, never by the sender-supplied filename.
S3 is a later backend behind the same interface.

## 5. Infrastructure

**New compose services**

- `rabbitmq` (`rabbitmq:3-management`), with a named volume.
- `worker` — `celery -A relaydesk.worker.app worker --loglevel=info`.
- `beat` — `celery -A relaydesk.worker.app beat --loglevel=info`.
- `greenmail` (`greenmail/standalone`) — development only. SMTP on 3025 and
  IMAP on 3143, backed by one store, so a real round trip is testable
  locally: an outbound reply we send lands in the same mailbox the poller
  reads. It is the default SMTP and IMAP target in `.env.example`, so a
  fresh clone can send and receive mail with no external account.

  Mailpit is the more familiar choice here and is deliberately not used: it
  serves SMTP, a web UI, and POP3, but no IMAP, so it cannot exercise the
  ingestion path at all.

`worker` and `beat` mount the same source bind mount as `api` and share its
image, so a code change is picked up without a rebuild.

**New environment variables** (added to `.env.example` with working
development defaults pointing at GreenMail):

```
CELERY_BROKER_URL=amqp://guest:guest@rabbitmq:5672//
INBOUND_DOMAIN=inbound.localhost
IMAP_HOST=greenmail
IMAP_PORT=3143
IMAP_USERNAME=relaydesk
IMAP_PASSWORD=relaydesk
IMAP_USE_SSL=false
IMAP_MAILBOX=INBOX
IMAP_POLL_SECONDS=60
SMTP_HOST=greenmail
SMTP_PORT=3025
SMTP_USERNAME=
SMTP_PASSWORD=
SMTP_USE_TLS=false
SMTP_FROM_NAME=Relaydesk
ATTACHMENT_DIR=/var/lib/relaydesk/attachments
ATTACHMENT_MAX_BYTES=26214400
```

All are added to `Settings` in `config.py` with the same defaults, so the
API and worker read one configuration object.

**New Python dependencies:** `celery[amqp]`, `aiosmtplib`, `aioimaplib`.
MIME parsing uses the standard library's `email` package — specifically
`email.parser.BytesParser` with `email.policy.default`, which is the modern
policy that decodes headers and handles multipart correctly. `mail-parser`
and similar are not needed.

## 6. Data model

Migrations continue slice 1's numbering, starting at `0007`. Enums follow
slice 1's established pattern: `enum.StrEnum` with
`sa.Enum(..., native_enum=False, create_constraint=True)`, producing
`VARCHAR` plus a `CHECK` constraint.

### New tables

**channel_accounts** — `workspace_id`, `kind` (`email`), `ingest_token`
(`String(32)`, unique), `display_name`, `active`. Indexed on
`workspace_id`. No credential column exists, by decision D4.

**raw_messages** — the immutable landing zone. `mailbox`, `uidvalidity`
(`BigInteger`), `uid` (`BigInteger`), `raw` (`LargeBinary`), `state`
(`fetched` | `ingested` | `unrouted` | `throttled` | `failed`), `error`
(nullable), `received_at`, plus `workspace_id`, `channel_account_id`, and
`external_id`, all nullable because none of them are known until routing
succeeds. Unique on `(mailbox, uidvalidity, uid)`.

**attachments** — `workspace_id`, `message_id`, `filename`,
`content_type`, `size_bytes`, `sha256` (`String(64)`), `storage_key`,
`inline` (bool), `content_id` (nullable). Indexed on `message_id`.

**poll_state** — one row per mailbox: `mailbox` (unique), `uidvalidity`,
`last_uid`.

### Modified tables

**messages** gains the six columns slice 1 deferred — `direction`
(`inbound` | `outbound`), `external_id` (`String(998)`, nullable),
`raw_message_id` (nullable FK), `in_reply_to` (`String(998)`, nullable),
`body_html` (nullable), `channel_account_id` (nullable FK) — plus
`delivery_state` (`none` | `queued` | `sent` | `failed`) and
`delivery_error`.

Logical dedupe is a **partial** unique index on
`(channel_account_id, external_id) WHERE channel_account_id IS NOT NULL AND
external_id IS NOT NULL`. It must be partial: Postgres treats NULLs as
distinct in a unique index, so a plain index would silently permit the
duplicates it exists to prevent on every outbound and seeded row.

`MessageRole` gains `system`, for bounce notices and delivery failures that
belong to a thread but were authored by neither a customer nor an agent.
Because slice 1's migration `0006` created these as named `CHECK`
constraints, adding a member means dropping and recreating
`ck_messages_role` — a `VARCHAR` column does not widen on its own.

**contacts** gains `bounced_at` (nullable).

**users** gains `notify_on_assignment` (bool, `server_default` true — an
existing-row default requires a server default, not just a Python one).

**workspaces** is unchanged. `slug` already exists and is globally unique,
so `<slug>-<ingest token>@<inbound domain>` is a valid, collision-free
address without a new column.

## 7. Inbound

### 7.1 Two tasks, not one

`imap_poll` (Beat-scheduled every `IMAP_POLL_SECONDS`) does no parsing. It
connects, fetches UIDs above `poll_state.last_uid`, writes each message's
raw RFC822 bytes to `raw_messages`, and enqueues one `ingest_message` per
row. `ingest_message` does everything else.

The split matters for two reasons. A message we cannot parse fails and
retries alone, rather than wedging the poll and stalling every other
workspace's mail behind it. And the raw bytes survive, so a message that
failed under a buggy parser can be replayed after the fix rather than being
lost.

**UID handling.** `poll_state` stores `uidvalidity` alongside `last_uid`.
IMAP servers may reset UIDs, at which point every stored UID becomes
meaningless. If the server reports a different `uidvalidity` than the stored
one, the poller resets `last_uid` to 0 and re-syncs. Without this the poller
silently ingests nothing forever after a server-side reset. Re-ingestion is
harmless because of the dedupe indexes.

**Dedupe is two indexes at two levels.** `raw_messages` is unique on
`(mailbox, uidvalidity, uid)`, so re-polling the same UID inserts nothing.
`messages` is unique on `(channel_account_id, external_id)` — the index
slice 1 specified — so a message that reaches the pipeline twice by any
route appends nothing the second time. The second index is load-bearing
under RabbitMQ, which is at-least-once: a worker that crashes after
committing will have its task redelivered.

### 7.2 Routing to a workspace

Forwarding does not rewrite `To:`. A customer mailing `support@acme.com`
produces a message whose `To:` header still reads `support@acme.com`; the
ingest address appears only in the SMTP envelope, which IMAP does not
preserve. Routing therefore reads, in order:

1. `Delivered-To` (added by Gmail and most forwarders)
2. `X-Original-To` (added by Postfix)
3. Any address in `To`, `Cc`, or `Bcc` on `INBOUND_DOMAIN`

matched against `channel_accounts.ingest_token`. Replies are unaffected by
this fragility: a customer replies directly to the tokenized address, so the
`To:` header is correct on every message after the first.

If no rule resolves, the raw message is marked `state = 'unrouted'` and
kept. It is never dropped and never guessed at. Unrouted messages are
visible to a deployment administrator through the CLI
(`relaydesk unrouted list`); a console surface for them is out of scope.

### 7.3 Classification, before threading

This gate runs before any conversation is created or appended, and it is
where the unglamorous correctness lives.

**Bounces.** Identified by `Content-Type: multipart/report;
report-type=delivery-status`, or a `From` of `MAILER-DAEMON` or
`postmaster`, or `Auto-Submitted: auto-replied` on a report body. A bounce
sets `contacts.bounced_at`, and attaches to the conversation named by its
`In-Reply-To` as a message with `role = 'system'`. It never creates a
ticket. A bounce that resolves to no conversation is marked `state =
'unrouted'`.

**Auto-replies and bulk mail.** `Auto-Submitted` present and not `no`,
`Precedence` of `bulk`, `auto_reply` or `list`, a `List-Id` header, or
`X-Auto-Response-Suppress`. These are filed onto their thread when one
resolves, and never trigger anything outbound.

**Loop prevention, both directions.** Relaydesk never sends automatically in
response to a message carrying any of the headers above, and every message
Relaydesk generates itself (invites, notifications) carries `Auto-Submitted:
auto-generated`. Without the pair, a support address and a vacation
responder will mail each other until one of them exhausts a quota.

**Rate cap.** A per-contact cap of 20 inbound messages per hour backstops
both. Over the cap, messages are stored with `state = 'throttled'` and not
threaded.

### 7.4 Thread resolution

Tried in the order slice 1 specified:

1. **Reply-address token.** Outbound mail is sent from
   `<slug>-<token>+c<conversation short id>@<inbound domain>`. A reply to
   that address names its conversation directly and unambiguously.
2. **`In-Reply-To` and `References`** matched against `messages.external_id`,
   scoped to the routed workspace. `References` is tried right to left.
3. **Same contact, same subject.** Subject normalized by stripping leading
   `Re:`, `Fwd:`, `Fw:` and bracketed tags, matched within 7 days.

No match creates a new conversation, allocating `number` through the same
`conversation_seq` mechanism slice 1 established.

Matching is always scoped to the workspace resolved in 6.2. A `References`
header is attacker-supplied; without the predicate, a crafted header would
append a message to another tenant's conversation.

### 7.5 Appending

Contact upsert on `(workspace_id, email)`. The conversation's `preview`,
`last_message_at`, and `unread` are updated exactly as slice 1's reply path
already does. An activity event is recorded. A conversation whose status is
`resolved` or `on_hold` reopens to `open` when a customer replies; `trash`
and `ignored` do not reopen.

## 8. Attachments

Parsed from the MIME tree, with `Content-Disposition: inline` parts that
have a `Content-ID` recorded as inline. Stored under `ATTACHMENT_DIR` at
`<workspace id>/<sha256>`, never under the sender's filename — that string
is attacker-controlled and a path traversal waiting to happen. The stored
`filename` column keeps the original for display only, sanitized of control
characters and path separators.

Total attachment bytes per message are capped at `ATTACHMENT_MAX_BYTES`;
past the cap, remaining parts are skipped and the message body still
ingests.

Served only through `GET /api/attachments/{id}`, which:

- resolves the row scoped to the caller's workspace, 404 for anything else,
  matching every other route in the product;
- returns `Content-Disposition: attachment` with a quoted filename;
- returns `Content-Type: application/octet-stream` for everything except a
  small allowlist of image types, so an inbound `.html` cannot be served
  inline from the application's origin;
- sets `X-Content-Type-Options: nosniff`.

Attachments are never exposed through a static file server.

## 9. Outbound

**The request path does not change.** `sendReplyAction` continues to write
its `Message` row through the existing service; the row is now written with
`direction = 'outbound'`, `delivery_state = 'queued'`, and a minted
`Message-ID`. The API then enqueues `send_email` and returns. The console's
behaviour is unchanged and still feels instant.

**The worker** builds the MIME message and sends it through
`aiosmtplib`. Headers:

- `From: "<workspace name>" <slug-token@inbound domain>`
- `Reply-To:` the same tokenized address including `+c<conversation>`
- `Message-ID:` the value already stored on the row
- `In-Reply-To` and `References` from the customer's last inbound message,
  so the reply threads correctly in the customer's own mail client
- `Auto-Submitted: auto-generated` only on system mail, never on agent
  replies, which are human-authored

Success sets `delivery_state = 'sent'`. Celery retries with exponential
backoff on transient failures — greylisting rejects a first attempt by
design, so a transient failure is normal rather than exceptional. Exhausted
retries set `delivery_state = 'failed'` with the error, and the thread
renders the message as undelivered.

**The reconciler.** Because publishing to RabbitMQ is not part of the
database transaction, a message can be committed as `queued` and never
published. A Beat task runs every five minutes and re-publishes any
outbound message still `queued` after two minutes. Re-publishing is safe
because `send_email` is idempotent on `delivery_state`.

## 10. The mailer

One module, `services/mailer.py`, with a single `send(to, subject,
text_body, html_body, headers)` entry point used by every system email. It
is the only place that talks to SMTP.

Templates are plain Python string templates, not a template engine — there
are three of them and a dependency is not warranted. Every system email is
sent as `multipart/alternative` with a text part, because a helpdesk that
sends HTML-only mail is a helpdesk that lands in spam folders.

## 11. Invites, re-enabled

Slice 1 disabled invites because acceptance issued a session for an address
nobody had proved they controlled, which was a cross-tenant account
takeover. The mailer resolves this directly, and the fix is the delivery
channel rather than a new check: **the invite token is sent to the invited
address and returned to nobody.** `POST /team/invites` no longer responds
with an `inviteUrl`; it responds `202` and mails the link. Possession of the
token is therefore proof of control of the address, which is the property
slice 1's README said re-enabling would require.

Accordingly:

- `POST /team/invites` and `DELETE /team/invites/{id}` lose their `503` and
  work.
- The public router (`GET /invites/{token}`, `POST /invites/{token}/accept`)
  is mounted.
- Invites expire after 7 days. Slice 1's model already has the column.
- The token is single-use: accepting deletes the invite row in the same
  transaction that creates the membership.
- The console's invite dialog reports "Invitation sent to <address>" rather
  than offering a link to copy.
- The README's "Team invites are not enabled" section is replaced.

`InviteRequest.role` becomes an enum rather than a bare `str`, closing a
deferred finding from slice 1 in the code this slice is already touching.

## 12. Assignment notifications

`users` gets `notify_on_assignment`, default true. When `set_assignee`
assigns a conversation to a user other than the actor, it enqueues a
notification email carrying the conversation subject, the customer, and a
deep link. Self-assignment never notifies. The preference is exposed on
`settings/account` through `PATCH /auth/me`.

## 13. API surface

New and changed routes, following slice 1's conventions: `/api` prefix,
camelCase JSON via the body alias generator, explicit `Query(alias=...)` for
query parameters, bearer auth, and 404 rather than 403 for anything outside
the caller's workspace.

```
GET    /channels/email                -> [{ id, address, displayName, active, createdAt }]
POST   /channels/email                { displayName } -> { id, address, ... }   admin
DELETE /channels/email/{id}           -> 204                                    admin

GET    /attachments/{id}              -> binary

PATCH  /auth/me                       { name?, notifyOnAssignment? } -> MeResponse

POST   /team/invites                  { email, role } -> 202                     admin
DELETE /team/invites/{id}             -> 204                                     admin
GET    /invites/{token}               -> { workspaceName, email, role }          public
POST   /invites/{token}/accept        { name, password } -> { token, expiresAt } public
```

`MessageOut` gains `direction`, `deliveryState`, and `attachments`
(`[{ id, filename, contentType, sizeBytes }]`). `ConversationDetail` is
otherwise unchanged, so the console's existing types extend rather than
break.

## 14. Web changes

- `settings/channels` reads `GET /channels/email` and drops
  `getEmailAccounts` from `lib/mock/settings.ts`. The email section shows
  each workspace address with a copy control and forwarding instructions.
  The "Connect Gmail" button is replaced by "Add address"; the Discord and
  one-click-import sections stay on mock data and keep their existing
  "coming soon" treatment.
- The thread renders attachments and an undelivered indicator for
  `deliveryState = 'failed'`.
- `settings/account` gains the assignment-notification toggle.
- The invite dialog reports a sent invitation.

## 15. Security

- No mailbox credentials in the database (D4).
- Ingest tokens are unguessable (D5).
- Thread resolution is workspace-scoped, because `References` is
  attacker-supplied (7.4).
- Attachments are content-addressed, never served inline, never served
  statically, and scoped on read (section 8).
- Invite tokens reach only the invited address (section 11).
- Inbound rate caps and loop prevention (7.3).
- Ingested HTML bodies are stored raw and are never rendered as HTML by the
  console in this slice; the thread renders the text part. Sanitized HTML
  rendering is deferred rather than done badly.

## 16. Testing

Following slice 1's structure: async pytest against a real Postgres, with
fixtures per workspace.

- **Parsing and classification** are pure functions over stored `.eml`
  fixtures — bounces, auto-replies, list mail, multipart with attachments,
  a message with no text part, and malformed MIME. These need no broker.
- **The pipeline** is tested by calling the async implementation directly,
  not through Celery. Tasks are one-line wrappers and are not where the
  logic lives.
- **Tenant isolation** gets explicit tests: a crafted `References` naming
  another workspace's message must create a new conversation rather than
  append; an attachment id from another workspace must 404.
- **Idempotency:** ingesting the same raw message twice appends one message.
- **SMTP** is tested against `aiosmtpd` in-process, asserting headers and
  that a failure sets `delivery_state = 'failed'` after retries.
- **Invites:** the response body must not contain the token; acceptance
  consumes it; a second acceptance fails; an expired invite fails.

## 17. Build order

1. Config, compose services, dependencies, GreenMail.
2. Celery app, the `asyncio.run()` bridge, Beat schedule, a trivial task
   proving the worker reaches the database.
3. Migration: new tables and the `messages` columns.
4. The mailer, plus assignment notifications as its first real consumer.
5. Invites re-enabled on top of it.
6. MIME normalization to `InboundMessage`, with fixture tests.
7. IMAP poller and `raw_messages`.
8. Routing and classification.
9. Thread resolution and appending.
10. Attachments, storage and the download route.
11. Outbound send, delivery state, and the reconciler.
12. Web wiring: channels, thread attachments, account toggle, invite dialog.

Steps 4 and 5 are early on purpose: they deliver a visible, testable
improvement — a real invite email — before any of the inbound machinery
exists, and they prove the mailer and the worker in one pass.

## 18. Known future consumers

**Portal, slice 3.** Contact magic-link sessions reuse this slice's mailer
and the `contacts` rows the pipeline creates.

**Provider webhooks.** A webhook adapter produces the same `InboundMessage`
and reuses classification, routing, and threading unchanged. Only sections
7.1 and 7.2 are IMAP-specific.

**Custom sending domains.** Per-workspace DKIM would change only the `From`
construction in section 9 and add a domain-verification flow.

**AI, slice 4.** `ingest_message` is where a triage or summarization job
would be enqueued, after the conversation is appended.
